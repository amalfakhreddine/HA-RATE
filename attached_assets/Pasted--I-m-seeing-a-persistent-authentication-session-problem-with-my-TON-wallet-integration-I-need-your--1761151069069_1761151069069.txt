 I’m seeing a persistent authentication/session problem with my TON wallet integration. I need your help to implement the server-side and config fixes so users who sign in with TonConnect remain logged in and can call protected endpoints (e.g. /start-mining) without getting 401: no wallet connect or being immediately logged out.

Problem summary
	•	When a user connects and signs with TonConnect the UI reports success, but any protected API call (e.g. POST /start-mining) returns 401: no wallet connect and the user is effectively logged out immediately.
	•	This occurs on Replit deployment (my frontend and backend are running on Replit). Behavior suggests the backend never receives a valid session token or cookie, or cookies are blocked by CORS/sameSite/secure settings.

How to reproduce (exact steps)
	1.	Open the deployed frontend at: https://<FRONTEND_REPL_DOMAIN>.repl.co (replace with the actual URL)
	2.	Click Connect Wallet and complete TonConnect sign flow.
	3.	Confirm UI shows signed-in (address shown).
	4.	Click Start mining (calls POST /start-mining).
	5.	Observe 401: no wallet connect response and user becomes logged out.

Observed behaviour
	•	/auth/verify may return OK, but subsequent requests to protected endpoints return 401.
	•	Browser network requests often show either no cookie sent or cookie blocked.
	•	Likely root causes: missing credentials on fetch, incorrect CORS response headers, cookies not set with correct attributes for cross-site, or server not issuing/validating a persistent session token.

What I need you to implement / change (priority list)
	1.	CORS with credentials
	•	Ensure the backend responses include:
	•	Access-Control-Allow-Origin: https://<FRONTEND_REPL_DOMAIN>.repl.co (exact front origin)
	•	Access-Control-Allow-Credentials: true
	•	Access-Control-Allow-Headers includes Content-Type, Authorization
	•	Ensure preflight OPTIONS requests succeed with those headers.
	2.	Set and send cookies correctly
	•	Backend must set the auth cookie as follows:
	•	HttpOnly: true
	•	SameSite: "None" (since front and back may be different origins)
	•	Secure: true in production (Replit provides HTTPS)
	•	Proper maxAge (e.g. 2 hours) and cookie name (e.g. btxl_session)
	•	Use res.cookie(cookieName, token, { httpOnly: true, sameSite: "none", secure: true, maxAge: ... })
	•	Make sure cookie domain/path allow the browser to send it when calls are made from the frontend origin.
	3.	Client must include credentials on fetch
	•	Ensure every fetch to the backend (auth verify, protected endpoints) uses:
	•	fetch(url, { credentials: "include", ... })
	•	This is necessary for the cookie to be sent/received.
	4.	Session/token handling
	•	After verifying the TonConnect proof, issue a server-signed token (JWT or server session) and set it in the httpOnly cookie.
	•	Verify protected routes read the cookie and validate the JWT. If the backend expects Authorization header instead, ensure front-end sends token (but httpOnly cookie preferred).
	5.	TonConnect proof verification
	•	Backend must validate the ton_proof signature (Ed25519) against the public key in the proof or walletStateInit. If publicKey is not included, parse walletStateInit per TON docs or fallback to on-chain check.
	•	Reject invalid signatures with 401 and return informative error messages.
	6.	Dev fallback option (for debugging only)
	•	For faster debugging, return the token in JSON after /auth/verify and allow the front-end to send it in Authorization: Bearer <token> while you sort cookies/CORS. (This is temporary and less secure — do not keep in production.)

Concrete files / env vars to check
	•	FRONTEND_ORIGIN environment variable should equal https://<FRONTEND_REPL_DOMAIN>.repl.co.
	•	JWT_SECRET or session store secret must be present and consistent across restarts.
	•	Ensure Replit’s HTTPS domain is used; cookie secure requires HTTPS.

Acceptance criteria / how I’ll verify the fix
	1.	After TonConnect sign/verify, browser receives an HttpOnly cookie (check Set-Cookie in response).

Security notes
